# 천장 뽑기 비교 실험

천장(pity) 시스템을 실제로 구현한 뽑기 모델입니다. 확률과 천장 규칙이 **완전히 같은** 두 버전을 만들고, 화면에 보여주는 정보만 다르게 해서 플레이어 행동을 비교합니다.

| 버전 | 보여주는 정보 |
|---|---|
| A · 손익분기점 명시 | 누적 지출(원), 손익분기점, 천장 카운트, 다음 1회 확률, 픽업까지 기대 잔여 비용 |
| B · 손익분기점 미명시 | 사용한 재화(원석)와 결과만. 금액·천장 카운트·손익분기점은 숨김 |

## 천장 규칙 (공통)

- 최고등급 기본 확률 0.6%
- 74회째부터 회당 +6%p (소프트 천장), 90회째 100% (하드 천장)
- 최고등급 중 픽업 50%, 실패(픽뚫) 시 다음 최고등급은 픽업 확정 → 최악 180회
- 1회 3,000원 / 160 원석
- **손익분기점** = 캐릭터 가치 ÷ 1회 가격 (기본 200,000원 ÷ 3,000원 = 66.7회)

픽업까지 기대 횟수는 약 93.4회(≈280,338원)이며, 천장 카운트별 기대 잔여 횟수는 역방향 동적계획법으로 정확히 계산합니다.

## 플레이어 행동 모델 (가정)

모든 플레이어는 심리적 예산(로그정규, 중앙값 = 캐릭터 가치)을 가지며, 픽업을 얻으면 멈춥니다. 두 버전에는 **같은 예산, 같은 난수열**을 넣으므로 차이는 정보 공개 효과만 남습니다.

- **A**: 다음 1회가 `min(예산, 손익분기점)`을 넘으면 멈춤. 단 기대 잔여 비용이 가치의 25% 이하면 천장을 마저 채움.
- **B**: 금액이 재화로 가려져 지출을 `perceive`(기본 0.7)배로 과소 인식하고, 뽑은 횟수에 비례해 매몰비용 때문에 한도가 늘어남(`sunk`, 90회당 +60%).

## 실행

```bash
python3 gacha_sim.py                     # 20,000명 비교표
python3 gacha_sim.py --value 300000 --perceive 0.6 --sunk 1.0
python3 gacha_sim.py --csv results.csv   # 플레이어별 결과 저장
python3 -m unittest test_gacha_sim       # 테스트
```

`index.html`을 브라우저로 열면 두 뽑기 기계를 직접 돌려 보고, 같은 모델로 집단 시뮬레이션 결과(지표 표, 지출 분포)를 볼 수 있습니다.

## 기본 설정 결과 (20,000명)

| 지표 | A 명시 | B 미명시 |
|---|---:|---:|
| 평균 지출 | 156,041원 | 262,400원 |
| 상위 10% 지출 | 198,000원 | 459,000원 |
| 픽업 획득률 | 16.9% | 85.6% |
| 손익분기점 초과 비율 | 0.6% | 76.1% |
| 심리적 예산 초과 비율 | 0.2% | 66.1% |
| 평균 순손익 (가치 − 지출) | −122,141원 | −91,220원 |

손익분기점을 보여주면 지출과 예산 초과가 크게 줄어듭니다. 다만 기본 배너는 기대 비용(약 28만 원)이 가치(20만 원)보다 커서, 손익분기점에서 멈춘 A 플레이어는 빈손으로 끝나는 경우가 많고 평균 순손익은 오히려 B보다 낮습니다. 손익분기점과 함께 시작 전 기대 비용도 보여줘야 손실을 줄일 수 있다는 뜻입니다. 행동 규칙은 가정이므로 계수를 바꿔 민감도를 확인하세요.

# 버튼 누르기 실험 (웹사이트)

천장(누를 수 있는 횟수의 한계)이 위험 감수 행동에 미치는 영향을 보는 실험입니다. 참가자는 각자 휴대폰이나 컴퓨터로 링크를 열어 과제를 하고, 결과는 연구자의 Google 스프레드시트에 모입니다.

| 집단 | 조건 |
|---|---|
| 통제 집단 | 버튼을 누를 수 있는 횟수에 제한 없음 (참가자에게 비공개인 안전 상한만 있음, 기본 200회) |
| 실험 집단 | 버튼을 최대 N번까지만 누를 수 있음 (기본 10회, 남은 기회 표시) |

두 집단의 과제는 같습니다. 버튼을 누를 때마다 성공하면 돈을 받고, 누를수록 성공 확률은 낮아지고 보상은 커집니다.

- 성공 확률: 95%에서 회당 −5%p (최저 5%)
- 성공 보상: 100원에서 회당 +100원
- 실패 시: 모은 돈을 모두 잃고 종료 (설정에서 "그 회차만 0원, 계속"으로 바꿀 수 있음)
- 참가자는 언제든 "그만하고 받기"로 모은 돈을 받고 끝낼 수 있음

## 파일

| 파일 | 역할 |
|---|---|
| `docs/index.html` | 참가자 페이지: 동의 → 참가자 ID → 안내 → 버튼 과제 → 받는 금액과 완료 코드 |
| `docs/admin.html` | 연구자 페이지: 집단 비교 결과, CSV 내보내기, 참가 링크, 실험 조건 설정 |
| `docs/config.js` | Apps Script 웹 앱 주소를 넣는 곳 |
| `apps-script/Code.gs` | Google 스프레드시트에 기록하는 서버 코드 (집단 배정, 중복 참여 차단 포함) |

`config.js`가 비어 있으면 **데모 모드**로 동작합니다. 기록이 그 브라우저에만 저장되므로 화면 확인용으로만 쓰세요.

## 설치 (한 번만, 약 10분)

### 1. 결과를 모을 스프레드시트와 서버

1. Google Drive에서 새 스프레드시트를 만듭니다 (예: "버튼 실험 결과").
2. 메뉴 **확장 프로그램 → Apps Script**를 엽니다.
3. 기존 코드를 지우고 `apps-script/Code.gs` 내용을 붙여 넣습니다.
4. 맨 위 `const ADMIN_KEY = 'change-me';`를 연구자만 아는 비밀번호로 바꾸고 저장합니다.
5. 오른쪽 위 **배포 → 새 배포** → 유형 **웹 앱**을 고릅니다.
   - 다음 사용자 인증 정보로 실행: **나**
   - 액세스 권한이 있는 사용자: **모든 사용자**
6. **배포**를 누르고 권한을 승인하면 `https://script.google.com/macros/s/…/exec` 주소가 나옵니다. 복사해 둡니다.

### 2. 웹사이트

1. `docs/config.js`의 `window.EXPERIMENT_API_URL = "";` 따옴표 안에 위 주소를 넣고 커밋·푸시합니다.
2. GitHub 저장소 **Settings → Pages**에서 Source를 **Deploy from a branch**, 브랜치는 이 코드가 있는 브랜치, 폴더는 **/docs**로 고르고 저장합니다.
3. 1~2분 뒤 `https://<GitHub 아이디>.github.io/<저장소 이름>/`에 참가자 페이지가, 같은 주소의 `admin.html`에 연구자 페이지가 열립니다.

GitHub Pages 대신 Netlify Drop(app.netlify.com/drop)에 `docs` 폴더를 끌어다 놓아도 됩니다.

### 3. 실험 진행

1. `admin.html`에서 비밀번호로 로그인하고 **설정** 탭에서 조건을 확인한 뒤 저장합니다.
2. **참가 링크** 탭의 링크를 참가자에게 보냅니다.
   - 기본 링크: 시작한 인원이 적은 집단에 자동 배정 (같으면 무작위)
   - `?g=c` 링크: 통제 집단 전용, `?g=e` 링크: 실험 집단 전용
   - 링크 끝에 `&pid=P001`을 붙이면 참가자 ID를 미리 채워 보낼 수 있습니다.
3. 참가자는 과제를 마치면 받는 금액과 **완료 코드**를 봅니다. 연구자 페이지의 같은 코드로 보상 지급을 확인할 수 있습니다.
4. **결과** 탭에서 집단별 평균 누른 횟수, 받은 금액, 종료 이유 비율, 분포, Welch t 검정을 보고 CSV로 내보냅니다. 원자료는 스프레드시트의 `runs`, `presses` 시트에도 그대로 있습니다.

### 실험 조건을 바꾸면

설정은 저장한 뒤 시작하는 참가자부터 적용되고, 각 기록에 그때의 조건이 함께 남습니다(CSV의 `cfg_` 열). `Code.gs`를 고친 경우에는 **배포 → 배포 관리 → 수정 → 새 버전**으로 다시 배포해야 반영됩니다.

## 기록되는 데이터

- `runs` 시트 (참가자 1명 = 1행): 참가자 ID, 집단, 배정 방식, 한계, 상태(진행 중/완료), 누른 횟수, 받은 금액, 종료 이유(그만둠/실패/한계 도달/안전 상한), 시작·종료 시각, 안내문 읽은 시간, 전체 소요 시간, 기기 정보, 그때의 조건
- `presses` 시트 (누름 1번 = 1행): 회차, 그 회차 확률·보상, 난수값, 성공 여부, 누르기 전후 금액, 과제 시작 후 경과 시간(ms)

시작만 하고 끝내지 않은 참가자는 `runs`에 "진행 중"으로 남아 이탈률을 볼 수 있습니다. 과제 도중 새로고침하면 그 자리에서 이어서 진행되고, 인터넷이 끊겨 결과를 못 보냈으면 기기에 보관했다가 다시 보냅니다.

## 알아둘 점

- 같은 참가자 ID와 같은 기기의 재참여는 기본적으로 막혀 있습니다(설정에서 허용 가능). 다른 기기에서 다른 ID를 쓰는 것까지 막지는 못합니다.
- 확률 추첨은 참가자 브라우저에서 이뤄집니다. 일반 실험에는 충분하지만, 참가자가 개발자 도구로 조작하는 것까지 막지는 못합니다.
